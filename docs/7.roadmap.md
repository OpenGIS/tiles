# 7. Roadmap

Phases 5 and 6 are complete and live. Phase 7 is hardening and deferred work. The live service serves
planet archives for `pois`, `routes` and `paths` built from the pinned 2026-10-26 snapshot, plus
on-demand `contours`.

| Phase | State             | Scope                                                                                                   |
| ----- | ----------------- | ------------------------------------------------------------------------------------------------------- |
| 1     | Complete          | PMTiles serving core.                                                                                   |
| 2     | Complete          | Vite and MapLibre development harness.                                                                  |
| 3     | Complete          | On-demand contours.                                                                                     |
| 4     | Complete          | Fixture and planet build pipelines.                                                                     |
| 5     | Complete and live | Provisioning, deployment, status, promotion, rollback and disposable remote build boxes.                |
| 6     | Complete and live | Production planet run: dated snapshot pin, filtered build, transfer and one-source-at-a-time promotion. |
| 7     | Next              | Hardening and deliberately deferred work.                                                               |

## Phase 5 — complete

Phase 5 is deployed at <https://tile.ogis.app> on a Hetzner CX23 in `nbg1` running Ubuntu 26.04. The
service runs under systemd as `ogis-tiles.service`, bound to loopback, with nginx terminating TLS
through certbot. Data lives under `/opt/ogis-tiles/data`.

- `ogis provision` rebuilds the existing server from cloud-init, with a dry run by default and a
  snapshot before a real rebuild.
- `ogis deploy` installs the application, production dependencies, systemd unit, nginx site, cache
  directories and TLS configuration.
- `ogis status` combines Hetzner Cloud state, SSH server state and HTTP health checks.
- `ogis promote` and `ogis rollback` validate a pair, restart the service, wait for readiness and
  verify the advertised build ID.
- `ogis build --remote` runs a disposable CPX62 build box, transfers each archive pair through the
  restricted build key and never promotes automatically.

Remote builds were first validated end-to-end on a CPX62 with the fixture POI build: preflight,
repository sync, `npm ci`, fixture build, restricted-key transfer to
`build@tile.ogis.app:pois/`, box destruction, then `ogis promote --source=pois`. Phase 6 then
repeated the flow with the production planet dataset.

## Phase 6 — complete

Phase 6 replaced the fixture archives with a filtered planet dataset. All three PMTiles sources were
built from the pinned snapshot, transferred to the live server and promoted one source at a time.
Contours remain generated on demand and are not built.

### Pinned snapshot

[`config/layers.json`](../config/layers.json) pins the snapshot:

- URL — `https://planet.openstreetmap.org/pbf/planet-261026.osm.pbf`
- date — `2026-10-26`
- SHA-256 — `63dfb50285e0b20e369963c49ce324ae38d5f0152337a7f7ad7ea66b914f8344`
- MD5 — `77397f0ffeb2dae22e56fda30b1f36aa`

Both digests are verified during the build. The planet date becomes part of the build ID
(`<YYYYMMDD>-<12 hex>`), so the date and the bytes describe the same snapshot. The manifest records
the verified MD5 pin in `planet.md5` beside the actual SHA-256 in `planet.sha256`.

### Verified flow

1. All three archives were built in one remote run on a disposable CPX62, which provides the disk
   for a filtered planet build. One shared osmium filter and a per-source Planetiler build produced
   the archive and manifest for each source.
2. Each archive pair was transferred through the restricted build key into
   `data/incoming/<source>/` and verified by SHA-256 against its `build.json`.
3. Each source was promoted separately with `ogis promote --source=<name>`, letting the restart,
   readiness wait and advertised build-ID check finish before the next source. Promotion rotated the
   live pair to `previous.pmtiles`, so rollback remains available.
4. The live checks passed after promotion: `/health` reports planet build IDs for all three sources,
   `/ready` returns 200, `/sources` and the TileJSON documents advertise the new versioned tile URLs,
   and a sample tile for each source returns `200 application/x-protobuf`.
5. The build box was destroyed after verification. Incoming is empty and the previous pairs are
   retained.

Refreshing the dataset repeats this flow with a new dated snapshot: update the pins in
`config/layers.json`, verify them against the provider's published values, rebuild on a remote box,
transfer, and promote one source at a time. Keep the previous pair until the next refresh is
validated. If a source is wrong, run `ogis rollback --source=<name>` and verify the restored build ID
before retrying.

## Phase 7 — hardening and deferred work

Phase 7 is the hardening phase. It covers the operational controls and automation deferred from the
earlier phases, including access control, traffic protection, monitoring and alerting, and scheduled
refreshes. The table records the deferrals and why each remains out of scope until a production need
makes it urgent.

| Deferred work                                   | Why it is deferred                                                                                                                           |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Application authentication and authorisation    | The API is public and read-only; there are no accounts or private layers. Add auth only when a use case requires it.                         |
| Rate limiting, request timeouts and concurrency | nginx terminates TLS but does not rate-limit. There is no global concurrency limit; upstream DEM quotas provide some natural backpressure.   |
| Monitoring and alerting                         | `/health` and `/ready` exist and can be scraped, but there is no external monitoring or paging yet.                                          |
| Scheduled planet refreshes                      | Planet updates are manual so the dated pin, transfer, promotion and rollback can be observed before automation.                              |
| Object storage, CDN or shared cache             | The server is single-node with local disk. A CDN or object store adds cost and operational surface before traffic justifies it.              |
| Archive watcher or reload signal                | Promotion and rollback restart the service explicitly; a watcher would add a second, less predictable reload path.                           |
| Local DEM cache or pre-generated contours       | Contours are generated on demand and avoid storing a worldwide contour set. A fallback is only needed if Mapterhorn availability demands it. |
| Automated capacity resize                       | The CX23 to CX33 upgrade is manual to avoid surprise cost and reboots. The preflight warns rather than resizing.                             |
| Automated backups beyond snapshots              | Provisioning snapshots cover rebuilds and the previous archive pair covers rollback. Off-site backups need a retention and restore policy.   |
| Multi-server or high availability               | One server keeps the data, cache and restart model simple. A load balancer and shared storage are a larger design change.                    |
| CI deployment                                   | Deploy is a deliberate local action with SSH, rsync and certbot. CI currently runs tests only.                                               |
| Unfiltered planet builds                        | They need about 850 GiB on the build box, beyond the default CPX62. The filtered pipeline is the supported path.                             |
| Production frontend                             | The Vite harness is a development tool. A public map or portal is a separate product decision.                                               |
| Code licence                                    | The repository has no root `LICENSE` or `NOTICE`; the licence decision is separate from the technical roadmap.                               |
