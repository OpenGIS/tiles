# 0. Terminology

Tile servers collect vocabulary the way a port collects languages. The words come from maps, binary
formats, build systems, cloud infrastructure and the peculiar shorthand of the people who run them.
The same word can mean several things at once: a _tile_ is a coordinate, a request, a file and a
rendered square; a _source_ is both an upstream dataset and an entry in this server's catalogue; a
_manifest_ is both the runtime configuration and a build record.

This page fixes the meaning of each term as this repository uses it. It is a map, not a dictionary:
follow the links for the detail. Terms are grouped by the part of the system where you meet them, and
each entry points at the page that turns the definition into practice.

> [!NOTE]
> Where the wider ecosystem uses a word differently, the difference is called out. The definitions
> describe this project, not the whole GIS world.

## Serving

These are the words that appear on the wire and in a client's configuration.

| Term               | Meaning here                                                                                                                                                                                                                                                                                                           | Read more                                                                        |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| Tile               | A square of map data addressed by zoom, column and row. This server returns vector tiles: a PMTiles tile read from an archive, or a contour tile generated for the request.                                                                                                                                            | [HTTP contract](2.architecture.md#http-contract)                                 |
| z/x/y              | The zoom level and the tile's column (`x`) and row (`y`) at that zoom. Tile routes accept `z` from 0 to 26 and require `0 <= x,y < 2^z`.                                                                                                                                                                               | [Status codes](2.architecture.md#status-codes)                                   |
| MVT                | Mapbox Vector Tile: a protobuf-encoded tile containing geometry, attributes and one or more named layers. It is the only tile format the server emits.                                                                                                                                                                 | [PMTiles reader](2.architecture.md#pmtiles-reader)                               |
| `.pbf`             | The file extension used for MVT tiles in this API. The same extension is used for OSM planet PBFs, so the docs say "planet PBF" or "OSM PBF" when the input is meant.                                                                                                                                                  | [HTTP contract](2.architecture.md#http-contract)                                 |
| Source             | A named entry in `config/layers.json` with a kind, title, zoom range and attribution; its tile URL is derived from the base URL. The shipped sources are `pois`, `routes` and `paths` (PMTiles) and `contours` (on demand). "Source data" means the upstream OSM extract; "source" alone means the configured service. | [Manifest](2.architecture.md#manifest)                                           |
| Source-layer       | A named vector layer inside an MVT or archive, such as `outdoor_pois`, `outdoor_routes`, `outdoor_paths` or `contours`. MapLibre styles target source-layers, not whole tiles.                                                                                                                                         | [TileJSON shape](2.architecture.md#tilejson-shape)                               |
| TileJSON           | The JSON document at `/<source>.json` describing a source: tile URL template, zoom range, attribution, bounds and vector layers. This server emits TileJSON 3.0.0.                                                                                                                                                     | [TileJSON shape](2.architecture.md#tilejson-shape)                               |
| PMTiles            | A single-file archive format for tiled data, designed for HTTP range reads. This server reads the archive from local disk; the repository includes its own PMTiles v3 reader rather than depending on the reference reader at runtime.                                                                                 | [PMTiles reader](2.architecture.md#pmtiles-reader)                               |
| Archive            | A `.pmtiles` file under `data/<source>/`. `current.pmtiles` is served by the unversioned route; `previous.pmtiles` is the optional rollback copy. Archives are not committed.                                                                                                                                          | [Data layout](2.architecture.md#data-layout)                                     |
| Versioned tile URL | `/<source>/<buildId>/{z}/{x}/{y}.pbf`. The build ID makes the URL immutable, so it can be cached for a year. Only PMTiles sources have versioned URLs.                                                                                                                                                                 | [Cache policy](2.architecture.md#cache-policy)                                   |
| ETag               | The validator on a tile response, built from the build ID, coordinates and encoding. A matching `If-None-Match` returns `304`.                                                                                                                                                                                         | [ETag and conditional requests](2.architecture.md#etag-and-conditional-requests) |
| Empty tile         | A `204` response with no body. It means the archive has no tile, the request is outside a contour zoom range, or the DEM coverage is missing; it is not an error.                                                                                                                                                      | [Status codes](2.architecture.md#status-codes)                                   |
| Health             | `GET /health`, which always returns `200` and reports `ok` or `degraded` with per-source availability and build IDs. It is a status report, not a readiness gate.                                                                                                                                                      | [Status and health](6.operations.md#status-and-health)                           |
| Readiness          | `GET /ready`, which returns `200` only when every local PMTiles source is available, otherwise `503` with the unavailable names. It never probes the DEM provider.                                                                                                                                                     | [Status and health](6.operations.md#status-and-health)                           |

## Data and build inputs

These are the things a build consumes or records. Most of them never reach the serving process.

| Term             | Meaning here                                                                                                                                                                                                                                                                    | Read more                                                            |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Planet           | The full OpenStreetMap planet PBF. A planet build is the production path; a fixture build uses a small committed extract instead.                                                                                                                                               | [Pinned snapshot](7.roadmap.md#pinned-snapshot)                      |
| Snapshot         | A dated copy of the planet data. The shipped manifest pins the `2026-10-26` snapshot by URL, date, SHA-256 and MD5. "Snapshot" also appears in operations for a Hetzner server image; the context makes clear which one is meant.                                               | [Pinned snapshot](7.roadmap.md#pinned-snapshot)                      |
| Pin              | A deliberately fixed input: a snapshot URL and date, a checksum, a tool version or a heap size. Pins make a build reproducible and let the manifest prove what went into it.                                                                                                    | [Toolchain and pins](5.pipelines.md#toolchain-and-pins)              |
| PBF              | Protocolbuffer Binary Format, the compressed OSM data format used as build input. The build reads a planet PBF or a fixture PBF; the server emits MVT `.pbf` tiles.                                                                                                             | [1. Prepare](5.pipelines.md#1-prepare)                               |
| Filter           | The osmium tag filter that selects the OSM features needed by every source. The pipeline renders one shared filter union, even for a single-source build, then strips version and user metadata.                                                                                | [Shared filter union](5.pipelines.md#shared-filter-union)            |
| Profile          | The Planetiler schema that turns filtered OSM data into one source's tiles. POIs use a YAML profile; routes and paths use Java profiles.                                                                                                                                        | [Profiles](5.pipelines.md#profiles)                                  |
| Planetiler       | The pinned Java tool that runs a profile and writes the PMTiles archive. Its jar is downloaded once and verified against a recorded SHA-256.                                                                                                                                    | [Stages](5.pipelines.md#stages)                                      |
| Fixture          | A small committed input for deterministic tests: the Alberta Canmore OSM extract, a 3×3 DEM block and a small POI archive. Fixture builds use the extract instead of the planet.                                                                                                | [Fixture and test split](5.pipelines.md#fixture-and-test-split)      |
| DEM              | Digital elevation model: the raster elevation tiles used to derive contours. The shipped source uses Mapterhorn WebP tiles in terrarium encoding.                                                                                                                               | [DEM provider and encoding](4.contours.md#dem-provider-and-encoding) |
| Contour          | An isoline of equal elevation, generated on demand from the DEM rather than stored in an archive. Each feature carries `ele` (metres) and `level` (0 minor, 1 major).                                                                                                           | [4. Contours](4.contours.md)                                         |
| Build ID         | The identity of the archive bytes: `fixture-<12 hex>` or `<YYYYMMDD>-<12 hex>`, where the hash is the first twelve characters of the archive SHA-256. Contour sources use a configuration-derived build ID instead.                                                             | [Output and build IDs](5.pipelines.md#output-and-build-ids)          |
| Run ID           | The identity of the build recipe: source, zooms, planet date and checksum, profile and filter hashes, skip flags and tool versions. It names the temporary work and staging directories and is separate from the build ID.                                                      | [Output and build IDs](5.pipelines.md#output-and-build-ids)          |
| Build manifest   | The `build.json` written beside an archive, recording input provenance, tool versions, profile and filter hashes, verification results and the archive hash and size. The installed copy is the `current.json` or `previous.json` sidecar; the server reads only its `buildId`. | [6. Manifest](5.pipelines.md#6-manifest)                             |
| Runtime manifest | `config/layers.json`: the versioned, validated configuration shared by the server and the build command. It is the single source of truth for sources, zoom ranges and build pins.                                                                                              | [Manifest](2.architecture.md#manifest)                               |

## Build and release

These describe how an archive travels from a build box or workstation to live data.

| Term              | Meaning here                                                                                                                                                                                                    | Read more                                                                |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `ogis`            | Shorthand in the docs for the CLI at `bin/ogis.mjs`, run as `node bin/ogis.mjs <command>`.                                                                                                                      | [Operations](6.operations.md)                                            |
| Build box         | A disposable, billable Hetzner Cloud server used by `ogis build --remote`. The default is a `cpx62` in `nbg1`; it is labelled, runs the same pipeline and is destroyed after a successful transfer unless kept. | [Remote builds](6.operations.md#remote-builds)                           |
| Incoming          | `data/incoming/<source>/` on the tile server, where a remote build deposits a verified archive pair. Nothing in incoming is served until it is promoted.                                                        | [Promoting and rolling back](6.operations.md#promoting-and-rolling-back) |
| Install           | The local `--install` step that copies built archives into `data/<source>/`, rotates a valid current pair to `previous` and restores the old files if any step fails.                                           | [Install and rollback](5.pipelines.md#install-and-rollback)              |
| Promote           | The deliberate step that validates an incoming pair, snapshots the live pair, installs and rotates it, restarts the service, waits for readiness and checks the advertised build ID.                            | [Promoting and rolling back](6.operations.md#promoting-and-rolling-back) |
| Rollback          | Installing the previous pair over the current pair, restarting and verifying the restored build ID. A rollback needs a previous pair; without one it fails without changing current.                            | [Promoting and rolling back](6.operations.md#promoting-and-rolling-back) |
| Content-addressed | Identified by a hash of the content rather than by a version number or timestamp. Build IDs are content-addressed; two builds with identical archive bytes share a build ID even if their recipes differ.       | [Output and build IDs](5.pipelines.md#output-and-build-ids)              |

## Operations

These are the words used when the service is running and something needs to change.

| Term            | Meaning here                                                                                                                                                                                                  | Read more                                                                                                     |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Deploy          | `ogis deploy`: sync the server code, install production dependencies, render systemd and nginx, issue or reuse TLS, restart the service and reload nginx. It preserves `data/` and never syncs `.env*` files. | [Deploying code and configuration](6.operations.md#deploying-code-and-configuration)                          |
| Provision       | `ogis provision`: rebuild the existing Hetzner server from rendered cloud-init. It does not buy the server or create DNS; a real rebuild snapshots the server first unless told not to.                       | [Rebuilding the server](6.operations.md#rebuilding-the-server)                                                |
| Edge            | nginx in front of the Node process on the live server. It terminates TLS, applies per-IP limits, caches source responses and writes the access log. The Node app binds loopback.                              | [Edge limits and throttling](6.operations.md#edge-limits-and-throttling)                                      |
| Cache           | Two different caches share the word. nginx keeps a bounded on-disk proxy cache per source; the contour source keeps bounded in-memory DEM and contour caches per process. Neither is a shared cache tier.     | [Cache policy](2.architecture.md#cache-policy), [Caching and ETag](4.contours.md#caching-etag-and-versioning) |
| Rate limit      | The per-IP nginx request and connection limits on tile routes. Excess requests get `429` with `Retry-After: 1`; health, readiness, the catalogue, the index and TileJSON are unmetered.                       | [Edge limits and throttling](6.operations.md#edge-limits-and-throttling)                                      |
| Access log      | The per-host nginx log in the `ogis` format, ending each line with `rt` (request time), `urt` (upstream time) and `cache` (cache status).                                                                     | [Reading the access log](6.operations.md#reading-the-access-log)                                              |
| Server snapshot | A Hetzner image taken before a provisioning rebuild, or the local backup of the live pair taken during promotion. It is a recovery copy, not the pinned planet snapshot.                                      | [Promoting and rolling back](6.operations.md#promoting-and-rolling-back)                                      |
| Status          | `ogis status`: a combined view of Hetzner Cloud state, SSH server state and public HTTP health checks. The scoped flags drop the cloud or SSH view.                                                           | [Status and health](6.operations.md#status-and-health)                                                        |

## Development

These are the local tools and test vocabulary.

| Term            | Meaning here                                                                                                                                                                                                                                      | Read more                                                                                   |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Harness         | The local Vite and MapLibre application under `dev/` that renders the vendored Canmore–Banff basemap and toggles the four sources. It is a development tool, not a production frontend.                                                           | [3. Dev harness](3.dev-harness.md)                                                          |
| Offline harness | The browser-test harness is deterministic and local: basemap, glyphs, sprites, PMTiles extract and DEM fixture are committed or vendored, and the test fails on external requests.                                                                | [Offline and deterministic behaviour](3.dev-harness.md#offline-and-deterministic-behaviour) |
| Smoke test      | The Playwright test that renders the harness, checks the source panel and attribution, asserts a real contour tile, and fails on console errors, page errors, failed responses or external requests. It is visual evidence, not a pixel baseline. | [Playwright smoke test](3.dev-harness.md#playwright-smoke-test)                             |
| Build suite     | `npm run test:build`: the end-to-end fixture build through Planetiler, osmium and the pmtiles CLI. It validates archives, manifests and sample tiles.                                                                                             | [Fixture and test split](5.pipelines.md#fixture-and-test-split)                             |
| Fixture mode    | A build from a local fixture PBF, used for development and tests. It is contrasted with planet mode, which requires a dated snapshot and a checksum pin.                                                                                          | [Command](5.pipelines.md#command)                                                           |
| `CONFIG_PATH`   | Selects an alternate runtime manifest. Relative `archiveDir` values still resolve against the repository root, not the manifest's directory.                                                                                                      | [Manifest](2.architecture.md#manifest)                                                      |
